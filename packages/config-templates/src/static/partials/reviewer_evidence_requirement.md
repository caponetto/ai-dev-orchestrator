- **Unverified findings** — Every finding MUST include an `evidence` field with a verbatim snippet from the diff proving the issue exists. If you cannot quote the exact content, you do not have sufficient evidence and MUST NOT report the finding. Never infer or reconstruct from memory — only cite what you can read.
- **Pre-existing pattern exclusion** — If the same pattern appears in unchanged lines of the same file or in other files this change did not modify, the change did not introduce it. Following an established (even imperfect) convention is not a blocking finding. For `critical`/`major`, evidence must come from added or modified diff lines — not from unchanged context you read while tracing data flow.
- **Cross-boundary claims** — When your finding's severity depends on behavior in code **outside** the diff (e.g., "the server does not validate X", "the controller will apply Y regardless"), you MUST read and cite that external code before reporting at `major` or `critical` severity. Do not infer behavior in another layer (backend, API, controller, upstream service) solely from the layer under review. If you cannot access the external code to verify your claim, cap the finding at `minor` severity and explicitly note the unverified assumption in the description.
- **Inferring behavior from variable names** — Do not treat variable names (e.g., `filteredValues`, `scopedOptions`, `userSpecificData`) as proof that a data source returns different results under different conditions. A variable named `filteredValues` might receive the same data as `allValues` if the source does not actually implement filtering. If your finding's consequence depends on a data source returning different/subset data per some parameter, you MUST verify this by reading the code that produces that data (e.g., the API handler, the query, the service method). Citing a fallback pattern (`filteredData ?? allData`) does not prove the two sources return different data.
- **Incorrect file paths** — The `file` field in every finding MUST use the exact path as it appears in the diff or repository. Do not guess, abbreviate, or restructure paths (e.g., do not write `.../Form/hooks/foo.ts` if the actual path is `.../app/hooks/foo.ts`, or `.../Form/components/Bar.tsx` if it is `.../Form/Bar.tsx`). Copy the path directly from the diff header or your file-reading output.
- **Defensive code ≠ proven defect** — If you see a fallback, a try/catch, a revalidation effect, or an async boundary with error handling, this is the developer building a defense against a possible state. It does NOT prove the problematic state is reachable or harmful. To report this pattern as `major`, you MUST independently demonstrate: (1) the concrete event sequence that triggers the problematic state, and (2) the observable harm when it triggers. If you cannot prove both, cap at `minor` and frame it as "potential hardening opportunity" rather than a correctness defect.
- **Copy/UX improvements are not correctness defects** — If your finding is that a warning or error message "could be more specific," "doesn't suggest a concrete alternative," or "is vague," this is a content enhancement suggestion, not a correctness issue. Cap at `minor` severity. Only elevate if the copy actively causes users to take destructive or irreversible actions they did not intend.
- **Fallback precision** — Claiming "no fallback" requires naming which fallback is absent: build-time feature flag, runtime degradation to an alternate data path, or reconnect preserving stale data. Overstating a missing reconnect UX as "no fallback at all" is a calibration error.
- **Permanent-state claims** — Claims that an error UI is permanent or never cleared require tracing the full client lifecycle (error set, reconnect, `onopen`, cleanup). If recovery clears the error, cap at `minor`.
- **Diff-vs-description completeness** — If the PR description, ticket, or commit message explicitly claims a file was added, modified, or deleted, but that file is absent from the actual diff (changed files list), flag this as a finding. A PR that claims to include a file but doesn't is incomplete. Severity: `major` (correctness) if the missing file is required for the feature to function (e.g., RBAC manifests, configuration files, migrations); `minor` if it's supplementary (e.g., documentation, examples). Quote the PR description's claim and note the file's absence from the diff as evidence.
