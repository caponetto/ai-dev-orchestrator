# Repository Model

The repository model lives under `packages/core/src/infrastructure/repository-model/`.

## Current Contract

The orchestrator stores configuration and runtime data under the global `~/.ai/` directory.

`ai init` creates:

```text
~/.ai/
  config.yaml
  roles.yaml
  governance.yaml
  runners.yaml
  templates/
    <role-id>.md
  scripts/
  runs/
```

The runtime does not load workflow files from `.ai/`. Built-in workflows ship with the repository in `packages/config-templates/src/static/workflows/`.

## Run Directories

Each run gets a directory under `.ai/runs/<run-id>/`.

Common files and subdirectories written by the current implementation include:

- `artifacts/`
- `config-snapshot.json`
- `inventory.yaml`
- `journal.md`
- `live-requests/`
- `live-responses/`
- `manifest.yaml`
- `report.md`
- `run.lock`
- `sessions/`
- `state.yaml`
- `workflow-definition.json`

On resume, the orchestrator uses model assignments saved in `config-snapshot.json`. Changing a
run's saved model affects its next dispatch without changing the global `~/.ai/roles.yaml`.

## Run IDs and Discovery

Run IDs are generated by the repository-model layer. Run discovery and status reporting are file-based and currently rely on markers such as `run.lock` and `state.yaml`.

`FilesystemRuntimeDirectoryManager` is responsible for creating run directories, listing runs, estimating status, and deleting run directories.

## Lock retirement and interrupted ownership

New lock acquisitions have an ownership token. Release verifies the full stored handle, claims
retirement for that acquisition and checks the owner again before unlinking. Releases and stale
reapers use the same permanent `run.lock.reclaim-<fingerprint>` claim. Only one remover can retire
an acquisition, so a delayed duplicate release cannot unlink a replacement owner's lock.
Successful retirement claims remain on disk; a new acquisition has a different fingerprint.
Do not prune claims while controllers or delayed cleanup operations might still be active.

An unreadable/partially published lock fails closed. A dead owner's lock with an interrupted
retirement claim also fails closed instead of letting a second reaper delete a possible successor.
If the lock was already removed before the process died, a fresh acquisition can proceed.
For a blocked run, inspect the lock, claim and process identity under exclusive maintenance;
reconcile them only after establishing that no owner or delayed remover can still operate.
A foreign host or uncertain process probe is not evidence that ownership is abandoned.

This is local filesystem ownership, not a distributed lease or power-loss guarantee. It assumes
all run writers respect the lock. Reconciliation of corrupted/manual files remains an operator
responsibility.
